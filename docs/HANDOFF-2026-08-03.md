## Product, in one paragraph

Unchanged from the prior handoff. Content analysis tool for an Indonesian social-media/marketing
agency (the user is the agency, not the creator). Paste an Instagram Reel/carousel or YouTube Short →
ScrapeCreators fetches metadata → video downloaded → Gemini watches and analyses → stored.
Destination is a **content brief generator**: name a topic, get a brief written in a specific
creator's style learned from ≥5 of their analysed videos (style fingerprint, #72, built). Not a
calendar, not a scheduler. Output language Indonesian; UI English. Desktop dashboard.

## Things that MUST be recorded

### 1. The linear-vs-gamma contrast error — and the process failure around it

**The technical error** is documented in full, with the correct procedure, in **RUNBOOK §8.4**.
Short version: `text-muted-foreground/70` was measured at **6.11:1 (passing)** by compositing its
alpha in **linear** sRGB. Browsers composite in **gamma-encoded** sRGB, where the true value is
**4.42:1 — below the WCAG 1.4.3 minimum of 4.5:1**. It shipped non-compliant through **#101 and
#102**, was caught only in #113 by a third agent using a different method, and was fixed by widening
`/70` → `/80` (~5.53:1) in
`app/app/analyses/components/counts/EngagementCount/constants.ts`
(`ENGAGEMENT_UNKNOWN_CLASSNAME`).

**The process failure is the more important half, and is why this is item 1.** Two agents
*independently* computed 6.11:1. That agreement was reported to the owner as **increased
confidence**. It was worth nothing: both had used the same wrong method, so they were not two
pieces of evidence, they were one piece of evidence counted twice.

> **Transferable lesson: agreement between agents that share a method is not verification.**
> Independent *agents* are not independent *evidence*. When two sources agree, ask what method each
> used before treating the agreement as confirmation. Cross-check with a *different* method — for
> contrast specifically, the browser's own DevTools readout, because it composites the way the
> browser actually does.

**Related standing hazard: the app is hard-locked to dark mode.** `app/layout.tsx` puts `dark` on
`<html>`; there is no theme toggle. The #96 design mockup was authored on a white surface, so its
`slate-*` values are WHITE-surface values and must never be transplanted literally. Full detail in
RUNBOOK §8.4.

### 3. PR #113 merged with a genuinely unresolved dispute — the tooltip re-open risk

**Status: unresolved, risk knowingly accepted by the owner, no follow-up ticket filed. This handoff
is the only record.** Whoever picks this up should start from the traces below rather than
re-deriving them.

**The claim (from a code review, traced through installed `@base-ui/react@1.6.0` source — version
and both line references verified again while writing this handoff):**

Clicking the (i) trigger a second time may **RE-OPEN** the tooltip rather than close it.

- `node_modules/@base-ui/react/floating-ui-react/hooks/useDismiss.js` **line 419** — outside-press
  listeners (`click`, `pointerdown`, `mousedown`, …) are attached to `document` with the capture
  flag set to `true`. A React **bubble**-phase `stopPropagation()` therefore cannot stop them; the
  capture-phase document listener has already run.
- `useDismiss.js` **line 222** — the "is this press on a trigger?" escape hatch keys off
  `store.context.triggerElements`, i.e. *registered* `Popover.Trigger` elements:
  `if (target && (triggers.hasElement(target) || triggers.hasMatchingElement(...)))`.
- **Our component deliberately renders no `Popover.Trigger`.** `CountInfoTooltip.tsx` passes the
  real `<button>` via `Positioner`'s `anchor` prop instead. So the button is *not* in
  `triggerElements`, that check does not fire for it, and the close-then-our-handler-reopens race is
  structurally available.

**The counter-evidence:** a separate agent drove **real Chromium via Playwright** against seeded
data and **could not reproduce it**. Click-toggle, click-to-close, and hover all behaved correctly.

**The tie was never broken.** Neither side was refuted. The source trace is sound and the empirical
test is sound, and they disagree. Do not treat either as settled.

**Why the risk is contained** (this is why the owner accepted it):

- The tooltip renders **only** for the `hidden` state, i.e. `like_and_view_counts_disabled = 1`.
- The owner's DB has **zero** such rows.
- The other surface it appears on (cards) is **unreachable** — see item 5 below / RUNBOOK §8.5.

So the code path is, in practice, not currently reachable in the owner's environment. That changes
the moment a creator-disabled post is analysed.

**Related architectural gap found while investigating (record it, it's real regardless of the
dispute):** Base UI's `FloatingFocusManager` gates behaviour on `openReason === REASONS.triggerHover`
(`node_modules/@base-ui/react/floating-ui-react/components/FloatingFocusManager.js:432`). Because our
component **bypasses the primitive's interaction hooks entirely** and drives `open` itself,
`openReason` **never becomes `triggerHover`** — so focus management activates on hover-opens too,
which is wrong for a hover tooltip.

**The reviewer's suggested fix — adopt `Popover.Trigger` — was argued against, and that argument
should be preserved:** `Popover.Trigger` imposes `aria-haspopup="dialog"` and focus-guard sentinels.
Both are correct for a dialog and **wrong for a hover tooltip**; adopting it to fix the dismiss
plumbing would trade a speculative bug for a definite accessibility regression. If someone revisits
this, the fix needs to address `openReason`/dismiss registration **without** taking on dialog
semantics.

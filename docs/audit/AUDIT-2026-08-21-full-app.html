P1 F-04 — The image-proxy disk cache is unbounded, attacker-keyable, and shares /tmp with the 500MB video downloader

BEavailabilityOWNER DECISION P1-PENDING — exploitability deliberately not tested source: Track A P0-1

Scope, after the 2026-08-24 owner ruling. This finding is now purely about the cache being unbounded and never evicted. The original write-up also carried a host-allowlist scope note and leaned on the proxy route being unauthenticated; both were removed, because the auth question is out of scope while the auth module is refactored. The disk-fill risk does not depend on who is calling the route — the cache is keyed on the full URL, and one legitimate authenticated session is enough to mint unlimited keys.

Location

  • lib/server/imageProxyCache/diskCache.ts:11-13 — cache key is sha256(full URL including the entire query string), fed by app/api/image-proxy/route.ts:119 (cacheUrl = targetUrl.toString()).
  • lib/server/imageProxyCache/diskCache.ts:65-80 — writeCacheEntry, which only ever does mkdir + two writeFile calls.
  • lib/server/imageProxyCache/constants.ts:4-5 — default directory is os.tmpdir()/image-proxy-cache. IMAGE_PROXY_CACHE_DIR is confirmed not set in production, so this is /tmp in the Linux container.
  • lib/server/analysis/downloader/download.ts:151 — path.join("/tmp", …), hardcoded, holding videos up to MAX_VIDEO_BYTES = 500MB.

What is wrong

Three things stack up.

  1. The key is the whole URL. Adding &cachebust=N to the target URL mints a brand new key and a brand new pair of files on disk, even though it is the same image.
  2. Nothing ever deletes a cache entry. A search of the whole module for every deletion primitive returns only a comment admitting the gap: 
    $ grep -rn "unlink|rm(|rmdir|evict|prune|delete|LRU" lib/server/imageProxyCache/
lib/server/imageProxyCache/diskCache.ts:60: * NOTE: no eviction/LRU/size-cap here by design (out of scope for this
lib/server/imageProxyCache/diskCache.ts:62: * flagged follow-up (candidate fix: periodic prune-by-mtime, or a
    The 30-day TTL only makes reads miss (diskCache.ts:41). A stale entry under a key nobody requests again stays on disk forever.
  3. The caller controls the key. The number of distinct entries a caller can create is bounded only by how many query-string variants they care to send, not by how many distinct images exist.

Why it matters to a user

If /tmp fills up, video analysis silently stops working. The video downloader writes to the same /tmp, with no quota separation. And nothing will alert anyone: cache writes are fire-and-forget (route.ts:181, void writeCacheEntry) and swallow all errors (diskCache.ts:77-79). The user would just see analyses failing for no visible reason.

Why this is P1-pending and not higher — stated honestly

A cache entry is only written after a successful 2xx upstream fetch (route.ts:181 runs after bufferResponse succeeds). Whether an Instagram CDN URL still returns 200 once extra query parameters are appended is the single open question that gates how fast the disk can be filled — those URLs carry their own upstream signature and may reject unknown parameters. This was deliberately not tested, because testing it means writing real files onto the production disk. It should be tested in a staging container, never in production.

Note that the growth problem does not need a hostile caller at all. Normal use also writes entries that nothing ever deletes, so the directory only ever grows.

Owner decision needed?

Yes. Either cap the cache (by size or entry count, with prune-by-mtime or LRU), or move IMAGE_PROXY_CACHE_DIR off the volume the video downloader uses, or both.

P1 F-06 — Migration tracking is not atomic: a crash in a one-statement window makes migration 012 re-run and DELETE FROM analyses

BEdata losssource: Track A P1-4

Location

  • scripts/migrate.ts:29-34
  • migrations/012_performance_block.sql:57 — DELETE FROM analyses;

What is wrong

Each migration file wraps itself in its own BEGIN TRANSACTION; … COMMIT;. Then migrate.ts records it in a separate statement afterwards:

:30  await db.executeMultiple(sql);
:31  await db.execute({ sql: "INSERT INTO _migrations …" });   // separate, not wrapped

Between the migration's COMMIT and that INSERT, the applied state is unrecorded. A crash, an OOM kill, or a Turso network blip in that window leaves the migration applied but untracked, so the next preDeployCommand run re-applies it. Migration 012 opens with DELETE FROM analyses;.

Why it matters to a user

Total, silent loss of the entire analysis corpus, triggered by a deploy. Every analysis costs real money and the owner's rulings say analyses are permanent inputs to one another.

Honest counter-argument

The window is one round trip wide and preDeployCommand runs rarely, so the probability is low. Also, production analyses is currently a handful of rows, so the loss today would be small. But the impact is unbounded and the fix is cheap. Low probability × catastrophic impact = P1.

Suggested fix direction

Record the _migrations row inside the migration's own transaction (strip BEGIN/COMMIT from the .sql files and let migrate.ts own the transaction), or at minimum make 012's DELETE conditional. This is a script fix, not a schema change — it does not touch the no-migration prohibition.

P1 F-07 — Migrations are tracked by filename only: editing an applied migration does nothing, silently

BEsource: Track A P1-5

Location

scripts/migrate.ts:8-12 (_migrations (name TEXT PRIMARY KEY, applied_at …)) and :20-23 (SELECT name FROM _migrations WHERE name = ? LIMIT 1).

What is wrong

There is no content checksum. If anyone edits an already-applied .sql file — to fix a CHECK constraint, an index, or a typo — the change never runs anywhere it was already applied. Development and production schemas then drift apart with no error and no log line.

Why it matters

A constraint you believe you fixed, but which was never applied, is worse than a constraint you know is broken. Independently confirmed in handoff 2026-08-20-c: "editing a migration's comment is provably inert".

Suggested fix direction

Add a checksum TEXT column holding sha256(file contents) and fail loudly on a mismatch. Do not auto-reapply.

P1 F-08 — A 10-URL batch cannot finish inside one HTTP request, and maxDuration = 300 enforces nothing on Railway

BEOWNER DECISION source: Track A P1-6, Track B B-P2-03

Location

  • app/api/analyze/route.ts:8 — export const maxDuration = 300
  • app/api/analyze/route.ts:53-64 — the sequential for loop
  • lib/server/analysis/constants/index.ts:1 — MAX_URLS_PER_BATCH = 10

What is wrong

Next.js's own docs say platforms can use maxDuration from the build output (node_modules/next/dist/docs/…/maxDuration.md:6). Railway does not read the Next build output: the Dockerfile ends with CMD ["node", "server.js"] on a standalone build. So maxDuration = 300 is decoration.

Meanwhile 10 URLs × 43–107 seconds each = 430–1,070 seconds of serial work inside one HTTP request. Track B2 measured the real per-analysis time live at 45–73 seconds, which is consistent.

Why it matters to a user

The browser holds one open request for 7–18 minutes with no feedback. If the connection is cut mid-batch, rows already marked completed survive, but the user is told the request failed. Paid work was done and the UI reports failure. The in-flight row can also be stranded — see F-09.

What is NOT wrong — a premise corrected

"Does URL 7 failing lose URLs 8–10?" No. The try/catch is inside the loop and collects into failedUrls. Track B2 confirmed this live: in a batch of 5, positions 1, 2 and 5 succeeded while 3 and 4 failed, and the loop still reached position 5 (created at 05:37:13, 05:37:58, 05:38:26).

Unverified

Railway's exact edge-proxy request timeout could not be determined from the docs or the CLI. Do not quote a number for it without checking.

Owner decision needed?

P1 F-12 — No security headers on any HTML response

BEsecuritysource: Track B B-P1-01, reproduces on main

Location

Every HTML document the app serves. next.config.ts contains only output: "standalone" — there is no headers() function, and proxy.ts injects no headers either.

What is wrong

None of Content-Security-Policy, X-Frame-Options, Strict-Transport-Security, X-Content-Type-Options or Referrer-Policy is present. The full observed header set was:

cache-control, content-encoding, content-type, date, etag, server, vary,
x-nextjs-cache, x-nextjs-prerender, x-nextjs-stale-time, x-powered-by,
x-railway-request-id, transfer-encoding, x-hikari-trace, x-railway-edge, connection

Why it matters to a user

Justification rewritten 2026-08-24. The original wording argued from the session cookie and the logged-in /app/analyses page. That reasoning is out of scope while the auth module is refactored, and it was never necessary: each of these headers is a baseline browser control that is missing on its own terms, regardless of who is looking at the page.

  • Clickjacking (X-Frame-Options / frame-ancestors). Nothing stops any third-party site from loading this app in an <iframe> and overlaying its own UI on top of it. A framing control is a page-level decision: either the app declares that it may be framed or it declares that it may not. This app declares nothing. Framing protection is the default expectation for an application UI, and there is no embedding use case here that needs it.
  • MIME sniffing (X-Content-Type-Options: nosniff). Without it, browsers are free to ignore the declared Content-Type and re-interpret a response as something else — for example treating a response the app intends as data as if it were script. The app already sets nosniff on the image-proxy response, so the header is understood to be wanted; it is simply not applied to the rest of the site.
  • Transport downgrade (Strict-Transport-Security). The app is HTTPS-only in practice but never tells the browser to enforce that, so the first request of any visit remains downgradeable.
  • Referrer leakage (Referrer-Policy). With no policy set, full URLs — including analysis ids in the path — are sent to third-party origins in the Referer header on any outbound navigation or asset load.
  • No content policy at all (Content-Security-Policy). There is no restriction on where scripts, styles, frames or connections may come from, so any injected markup executes with the full privileges of the page.

None of these depend on a login state. This is a next.config.ts change that touches no auth code and can ship independently of the auth refactor.

Suggested fix direction

Add a headers() block to next.config.ts (or set them in proxy.ts) with frame-ancestors 'none', nosniff, HSTS and a Referrer-Policy. Bundle F-24 (poweredByHeader: false) into the same change.

PRD §13.1.1 asks for completeness of information, not five widgets. Each of the five questions is assigned to the shallowest level that can honestly carry it. Nothing that prevents a misread lives above L1. That split is what makes R-13.6.2 auditable.

String 3 is the one R-13.5.3 was written for — and it needs a schema change

On an all-image carousel the like_and_view_counts_disabled flag is absent from the payload entirely — not false, absent. Absence means we cannot tell. So the app must not say “creator hid the counts”, because we do not know that.

  • A distinct stored value is required (R-13.5.3a). Two different facts cannot share one enum or the UI is structurally unable to tell the truth. Naming is the tech lead’s call; that it exists is a design requirement.
  • The copy deliberately says “We can’t tell”. It is longer and less tidy than string 1. It should not be edited. A tidier UI string is not a reason to assert a fact we do not have (R-13.5.3b).
  • If V1 later shows the flag is reliably present on this payload shape, this string can be retired. Until then it stands — approved is not verified (R-13.5.3c).

The badge is not dismissible, does not fade, and is not hidden in Compact density. A provisional score must never be presentable as final.

R-13.4.4 — banned phrasings

The maturity floor is a tunable estimate, not a measured constant (caveat C1). Nobody has data on how long a post takes to settle. So no user-facing string states the number of hours — the copy says “for their first few days”, vague on purpose. A specific number would read as researched.

Never: “posts settle after 72 hours” · “the standard settling window” · “research shows” · “typically stabilises within”. Not in copy, and not in a code comment that could later be lifted into copy. AC-29 asserts this by string search.

The elephant: the 1–5 is a judgement, not a measurement

The computed layer produces 4.1% of views and 3.2× their usual — both traceable to stored operands, both fully explainable. The 1–5 is produced by Gemini (PRD §4.1, §5.2), and its relationship to those ratios is a model judgement with no stored derivation. So when a user asks “why 4?”, the only honest answer is the ratios plus Gemini’s prose — and R-13.1.2 arguably forbids the shallow version of that as “a restatement of the number.”

There is also a live confusion risk the table makes vivid: a row can show performance 2 next to 3.2× their usual, and nothing in the current design explains why.

Proposed treatment
  1. Label the 1–5 as a read: “The 1–5 is a judgement of the numbers below, not a number we measured.”
  2. Put the measured figures above the judgement in the popover. Reading order is an argument about which number to trust.
  3. Present drivers[] as the reasoning, in Gemini’s Indonesian, unedited, under “Why it did what it did”.
  4. When score and multiplier disagree, say so: “This scored lower than the reach multiplier suggests — the reach was strong but engagement on it was not.”

The design cannot backstop a bad string there. It has to be fixed in the prompt (R-12.5.4).

Things in §13 I think need PM / owner attention — flagged, not designed around

  1. “based on N videos” is factually wrong on an image bucket. R-13.4.1 and AC-28 mandate the literal word. Rendering “based on 5 videos” under a figure computed entirely from image carousels reintroduces the same class of error as labelling a play count “Views”. I propose a bucket-aware noun — based on 7 reels / 6 carousels / 5 Shorts, generic fallback based on N posts — which needs AC-28 relaxed from the literal string to the pattern based on {N} {noun}. PM/owner call.
  2. R-13.3.4 is unachievable as written. “Every numeral in an explanation exists in the computed block” — the 5 in “2 of 5 carousels” is a config threshold and the week in the staleness copy is a TTL. Resolved for the threshold (allow-listed, R-14.2.7); the week is still open. Either the computed block stores it, or the allow-list is extended. Cheap either way; it will fail AC-27 if nobody decides.
  3. The 1–5 score’s explainability is the weakest link in §13 (see above). Needs a ruling on the proposed “label it as a judgement” treatment — or on dropping it from the table entirely in favour of the multiplier.
  4. confidence and tierUsed overlap. Tier 3 is never high-confidence; a follower denominator is capped at medium. Showing both at L1 may read as two independent judgements when it is largely one. I would keep the tier phrase at L1 and demote the confidence word to L2.
  5. The “both readings” sentence needs a high/low threshold that §3.4 forbids sourcing from an industry benchmark.
  6. R-13.5.3a’s stored reason exists — CAUSE_NOT_DETERMINABLE. Resolved 2026-08-09. It shipped in merged migration 012 and is live in the perf_unavailable_reason CHECK constraint (TDD §5.2), carried into 013. The earlier text here — “R-13.5.3a’s new stored reason does not exist yet” — is superseded, as is the proposed name PERFORMANCE_DATA_ABSENT, which was ruled against because CAUSE_NOT_DETERMINABLE names the epistemic state rather than the data state (TDD §5.3). String 3 is renderable and AC-30’s negative assertion has a distinct value to assert against.
  7. Nothing in §13 says what happens on re-analysis. Scores are frozen (D8), but if a user can see two scores for the same post with different values, the as-of framing is doing a lot of work and may not be enough.

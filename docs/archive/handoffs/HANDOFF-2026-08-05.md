### Ticket #73 — style fingerprint read + human override API: full three-part chain

Split from `docs/archive/specs/TDD-fingerprint-read-override-api.md` §8. The parent issue was closed
with a summary comment mapping **every** acceptance criterion to what shipped.

**#115 / PR #120 — the lib layer.** Migration 011 (`computed_at`, nullable, backfilled from
`updated_at`, written only by `upsertFingerprint` so it stays "last recompute time" even after a
human PATCH), `NON_OVERRIDABLE_FIELDS` enforcement at both write and read, `validateOverridePatch`
reusing #65's taxonomy guards, and the partial-patch primitive.

**This PR went through TWO genuine bugs found in review, both structural:**

1. **A connection leak in `@libsql/client`'s local sqlite3 driver.** `Sqlite3Client.transaction()`
   steals the client's underlying `Database` handle and nulls `this.#db`, so the client can never
   close it; `Sqlite3Transaction.close()` is a **no-op after a successful commit**. There is no
   userland fix — `finally { tx.close() }` is already correct and is not enough. Harmless in tests;
   **unbounded under a long-lived Next.js server once #116 made it per-PATCH-request.** Verified in
   driver source (`lib-esm/sqlite3.js:155-158`, `:205-209`, `:272-276`), not accepted on report.

   **The fix was to remove the transaction entirely**, rewriting the merge as a **single atomic
   `UPDATE ... RETURNING *`** that computes the whole merge inside SQLite using `json_set` /
   `json_remove` over the row's own current `overrides` value. This is *more* atomic than what it
   replaced — the old version had a SELECT and an UPDATE as two round trips inside `BEGIN`; the new
   one has neither. `RETURNING` emitting zero rows is what distinguishes NOT_FOUND from a no-op
   update.

   Because that rewrite introduced dynamically-constructed SQL, it was **re-reviewed on Opus
   specifically for injection surface** and passed a rigorous adversarial pass: no caller-controlled
   character ever reaches the SQL text (patch input controls only *how many* wrappers and *which of
   two*), keys are always bound `?`, values always `json(?)` over `JSON.stringify`. The reviewer also
   exercised json1's own path grammar directly against crafted keys (`a.b`, `$.x`, `a[0]`, `a"b`,
   `","$.evil","x`) and confirmed no path traversal or breakout is reachable — worst case is a thrown
   `SQLITE_ERROR`.

2. **A prototype-chain lookup vulnerability.** A patch arrives via `JSON.parse`, so keys like
   `constructor`, `__proto__`, `toString`, or `hasOwnProperty` land as ordinary own-enumerable keys.
   The validator's `KEY_VALIDATORS[key]` lookup walked the prototype chain and returned a real
   `Object.prototype` member instead of `undefined` — either silently "validating" an unknown key or
   throwing a raw TypeError that would surface from the route as an **uncaught 500 instead of a 400**.
   Fixed with an explicit `Object.hasOwn(KEY_VALIDATORS, key)` guard
   (`lib/server/fingerprint/validation.ts:174`), pinned by regression tests in
   `tests/server/fingerprint/validation.test.ts` (`constructor`, `__proto__` via real `JSON.parse`,
   `toString`, `hasOwnProperty`, plus a mixed valid/invalid key case asserting only the bad key is
   reported) and one route-level test asserting **400, not 500**.

   > **Accuracy note for whoever reads this next:** this was found during **PR #121's** review (the
   > route), not #120's, and was fixed as a follow-up into the validation layer. The test file
   > comments say "PR #121 review follow-up" — that is correct, don't "fix" it.

**#116 / PR #121 — the route.** `GET`/`PATCH /api/profiles/[id]/fingerprint`, auth-guarded, `params`
awaited per this Next.js version's contract. 404 is split into `PROFILE_NOT_FOUND` vs
`NO_FINGERPRINT` (the latter carrying `analysisCount`/`required`), because a cold start with <5
qualifying analyses is a **normal product state, not an error**. Verified not only by 14 unit tests
but against a **real running app** — seeded profile + 5 completed `schema_version=2` analyses, real
`recomputeFingerprint`, live `curl` against every path including 401s and the invalid-enum 400.

**#117 / PR #122 — the client data layer.** `lib/api/fingerprint/{api,hooks,types,constants,helpers,index}.ts`.
`api.ts` returns the server payload verbatim (zero reshaping, per AGENTS.md); all derivation lives in
`hooks.ts`'s `select`. A 404 **resolves to typed absence rather than throwing**. Notably it shipped
with a **type-level fix** such that a regression to passing a raw function reference instead of a
computed value in `select`'s output is a **compile error**, not a lint nit. **No UI, no page, no host
surface** — deliberate, per the ticket.

### Ticket #123 — the jsdom harness, and a three-round verification case study

**PR #126** added a jsdom + React Testing Library environment as a **second vitest project** inside
the single `vitest.config.ts` (`test.projects`, vitest 4's replacement for `defineWorkspace`) rather
than flipping the global environment. The node suite stays exactly as fast and DOM-free as before;
`npm run test` and CI needed **no changes**. Dep versions were chosen against the pinned Node
`24.14.1` (`jsdom@29.1.1`, because `jsdom@30` requires `^24.15.0` and is simply not installable here).

**This is the session's best case study in verification actually catching real bugs, and it took
three rounds.** Recording it plainly:

- **Round 1** found two harness-correctness bugs, both of which every future jsdom test file would
  have inherited: (a) a **glob-routing bug** — the node project's `tests/**/*.test.ts` glob also
  matches a `.dom.test.ts` file, so a jsdom test could silently run in the wrong environment; and (b)
  **RTL's auto-cleanup was silently disabled**, because it only self-registers when `afterEach` is a
  global and the project sets `globals: false`.
- **Round 2** found that the round-1 fix had introduced *new* problems: (a) four **literal NUL bytes**
  in `tests/config/vitestProjectGlobs.test.ts` (a raw-NUL sentinel), which made git classify the file
  as **binary** — every future diff of it would have been unreviewable; (b) doc count drift in RUNBOOK
  §7; and (c) React's **`IS_REACT_ACT_ENVIRONMENT` was also silently unset** — the *same root cause
  class* as the cleanup bug, from the same `globals: false` setting.
- **Round 3** confirmed everything genuinely fixed by **independent empirical verification, not by
  reading the code or trusting the PR description** — `od -c` on the git blob plus
  `git diff --numstat` reporting `99 0` instead of `- -` (the authoritative signal git no longer sees
  binary), RTL/react-dom source for the act-environment mechanism, and independent per-project test
  re-runs for the counts.

Each of the two harness bugs is now pinned by its own regression test
(`tests/setup/domCleanup.dom.test.tsx`, `tests/setup/reactActEnvironment.dom.test.tsx`), and the glob
fix by `tests/config/vitestProjectGlobs.test.ts`. The demonstration test was also proven
**non-vacuous** by temporarily removing the invalidation it asserts and confirming it fails.

> **Naming convention, now load-bearing:** a jsdom test MUST be named `*.dom.test.ts(x)`. A plain
> `*.test.tsx` with no `.dom.` segment matches **neither** project and silently does not run at all.
> RUNBOOK §7 has the full reasoning.

**Where #123 came from:** it was filed as a **follow-up from PR #122's review (ticket #117)**, which
observed that the fingerprint client's mutation-invalidation contract was verified only "by
construction" — both hooks use the same query-key factory, statically true but never exercised. That
was acceptable *only* because there are zero consumers; it stops being sufficient the moment a real
component renders this data. **#123 is that issue's number** — it was filed and closed in the same
session.

`--card` 7.57:1, `--popover` 7.38:1, `--muted` 6.78:1, `--secondary` 6.46:1) — it clears 4.5:1 on all

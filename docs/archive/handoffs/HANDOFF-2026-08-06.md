## 4. The open PR — #154 — DO NOT MERGE

**PR #154** (`jonathan/141-tier2-baseline`, ticket **#141** / 3B-3), +741 lines across
`lib/server/analysis/performance/baseline.ts`, `types.ts`, `index.ts`, and
`tests/server/analysis/performance/baseline.test.ts`.

**Review verdict: DO NOT MERGE — 2 blocking defects.** Full review (the authoritative artefact, read
it before touching the branch):
<https://github.com/jordanjordann/my-content/pull/154#issuecomment-5203504770>

Both blockers are in `metricFor()`, and both land on **R-4.3.2** (a ratio may only combine values of
the same reach kind; mixing must fail loudly).

### Blocking 1 — an unavailable-reach reel poisons its entire bucket, permanently

`metricFor()` infers the denominator from **whether `perf_reach_value` happens to be populated**. In a
reach bucket a `NULL` reach does not mean "engagement-denominated" — it means **reach was not
resolvable for a post that is reach-denominated** (`perf_reach_derived_from = 'NONE'`, hidden
play/view counts). One such reel in `instagram:reel:full_video` gets relabelled `ENGAGEMENT_COUNT`,
`denominatorsSeen.size` becomes 2, and `computeBaseline()` **throws for every subsequent analysis in
that bucket** until the creator's history changes.

The PR's own first mixed-denominator test constructs exactly this row and calls it "deliberately
mismatched". **It is not a corrupt fixture; it is what a reach-hidden reel looks like in production.**

**Fix:** the denominator must be derived from the **bucket / `perf_reach_derived_from`**, never
inferred from the presence of a value. A reach-denominated post with unresolvable reach must be
**skipped (`return null`)** — excluded, not reclassified, not thrown on. This matches the owner's own
words on #141: *"a `NONE` post … contributes no baseline sample either way."*

### Blocking 2 — the silent one, and the more important of the two

`usableCount(null)` returns `0`, so `metricFor({ reachValue: null, likeCount: null, commentCount: null })`
yields `{ ENGAGEMENT_COUNT, 0 }`. A hidden-count image carousel therefore becomes a **valid baseline
sample worth zero engagement**: it pushes `sampleSize` toward the threshold **and** drags the median
down, which **inflates every multiplier computed against that bucket.** This is precisely the "reads
3.2× when the truth is nearer 1.3×" failure the ticket exists to prevent, and unlike Blocking 1 it
**fails silently**.

> **Do not "fix" this in `ratios.ts`.** `usableCount`'s `null → 0` is **correct there** (shipped in
> #140, merged) — the question there is "what is this post's engagement total". In the baseline path
> the question is "does this post qualify as a comparator at all", and the answers legitimately
> differ.

### Required before #142 — the phantom bucket

`analysis_mode` is `TEXT` with **no `NOT NULL`** (`migrations/012_performance_block.sql:93`), and
`pipeline/index.ts:84` **explicitly resets it to `NULL` on the re-analysis path**. `computeBucketKey()`
does zero runtime validation, so `[platform, mediaType, null].join(":")` yields the plausible-looking
`"instagram:reel:"` — a phantom bucket pooling everything that lost its mode, with `bucketNoun()` still
returning `"reels"`. #142 reads these off a DB row where libsql types them `string | null`; **one
`as AnalysisMode` cast and this ships.** Needs a loud runtime throw on a null/unrecognised `platform`,
`mediaType`, or `analysisMode`.

### A wrong doc comment that #142/#143 would build on

`baseline.ts:33-37` claims a single image post splits out as `analysis_mode = 'images_only'`. **It does
not.** `resolveMediaParts()` returns an **empty** part array for a lone image post, so `analysisMode`
never leaves its `'metadata_only'` initial value — **`instagram:post:images_only` is unreachable**, and
lone image posts land in `instagram:post:metadata_only`. Not a defect (the key still separates them),
but the *justification* is what the next two tickets build on.

### Non-blocking, all from the same review

`MATURITY_FLOOR_HOURS` is never referenced by `baseline.ts` (tests hardcode `72`, so an env override
would diverge silently from prod); `median === 0` yields a non-null median with a null multiplier,
contradicting `BaselineResult`'s own doc; rows with `perf_post_age_hours IS NULL` are implicitly
dropped by `>= ?`; `MediaType` is re-declared rather than imported from `classifier/rules.ts`;
`baseline.ts` does barrel duty with a bottom-of-file `export type … from "./types"`; `bucketNoun()`
returns `string` rather than a union of the five nouns; no `LIMIT` on the candidate query.

### Confirmed correct — do NOT touch while fixing

Median not mean (TDD §6). Single `db.execute()`, **no `transaction()`** — the `@libsql/client` leak is
avoided. `BASELINE_MIN_SAMPLE` imported not hardcoded, env-overridable at 5. Sample size disclosed at
every state including sub-threshold. **Self-exclusion and schema-version isolation are
mutation-verified.** The bucket key `${platform}:${mediaType}:${analysisMode}` was **adjudicated
correct** by the review against PRD §4.2 — `media_type` alone would pool video-bearing and all-image
carousels. The reviewer independently reproduced all three of the PR's mutation proofs.

**Suite state on that branch: 419 tests / 34 files, green** — which is the point. See §8.

### Reach fields — verified from committed fixtures (zero spend)

- **Top-level reels:** `video_view_count` can be **`0`** while the truth sits in `video_play_count`
  (fixture: `0` vs **116,333**).
- **Carousel video children: the fields are REVERSED** — `video_play_count` is `null` on all 7 video

- On a real reel, **views ≈ 42% of plays** (305,044 vs 721,558). These are **different quantities**, not

- Hence **R-4.3.2**: a ratio may only combine values of the **same reach kind**; mixing must fail

> **Practical consequence for Tier 2's cold start.** Because plays and views are not interchangeable

> phrase "5 per creator per reach kind" appears **nowhere** in the TDD or PRD. **Worth putting to the
> owner explicitly** — it is a product-visible cold-start cost that no approved document currently

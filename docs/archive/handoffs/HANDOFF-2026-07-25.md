## Product, in one paragraph

Content analysis tool for an Indonesian social-media/marketing agency (the user is the agency, not the creator). Paste an Instagram Reel/carousel or YouTube Short → ScrapeCreators fetches metadata → video downloaded → Gemini watches and analyses → stored. Destination is a content brief generator: name a topic, get a brief written in a specific creator's style learned from ≥5 of their analysed videos (style fingerprint, #72, now built). Not a calendar, not a scheduler. Output language Indonesian; UI English. Desktop dashboard.

### #71 → PR #95 — carousel, migration 009
Carousel: N media parts (images + video) in one Gemini call. Ticket had extensive fixture-verified spec corrections (C1–C9) from a real captured carousel payload — view-count semantics **invert** between reels (`play_count` real, `view_count`=0) and carousel children (`view_count` real, `play_count`=null); this is now correctly branched and tested per-type, never merged into one field.

**First review found a real blocking bug that shipped with green tests**: carousel images were being mime-typed via `filePath.split(".").pop()` on a raw CDN URL (works for local `/tmp/x.mp4` paths, returns garbage on `...jpg?stp=...&_nc_ht=...`), so every carousel image would've hit Gemini as `application/octet-stream` (rejected) in production — while the test suite passed because the test mocked away the exact function that was broken. Fixed with real magic-byte sniffing + URL-pathname fallback, and the new regression test uses a **verbatim, unmocked** fixture URL. This is the single most important verification catch of the session — a textbook "green CI, broken prod" case, only found by reading code against real data, not by running tests.

Fix round also added `coauthor_producers` (JSON array) and `like_and_view_counts_disabled` (nullable bool) columns to migration 009 (owner-approved, done while the table rebuild was already open, avoiding a second rebuild), `MAX_IMAGE_BYTES` cap, and RUNBOOK §7 update.

### #72 → PR #99 — style fingerprint, migration 010

**Review found a real, subtler bug**: the read-path merge in `getFingerprint` spread `overrides` *before* hardcoding `consistencyIndex` from the row, so an override on `consistencyIndex` would be silently ignored on read while `overriddenKeys` still claimed it was overridden. Verified independently on a fresh clone, not just the developer's worktree.

## Recovered process incident — worth reading if repeated

Around merging PR #105, the main checkout's `HEAD` file pointed at `be-100-surface-engagement-counts` while `git worktree list`'s internal bookkeeping still claimed this directory was on `main` — a metadata desync, almost certainly caused by an earlier agent (likely a merge-only agent dispatched without `isolation: "worktree"`) running raw git operations in the shared main directory. `git checkout main` failed with a worktree-lock error as a result. Working tree was clean throughout (verified before touching anything), so it was safe to repair directly with `git symbolic-ref HEAD refs/heads/main`, then a normal `git merge --ff-only origin/main` completed the fix. No data was lost, but **this is a second class of hazard from working in the shared checkout** (the first being the crashed-agent write-isolation guard above). **Recommendation for next session: pass `isolation: "worktree"` on every single dispatch, including merge-only tasks, no exceptions** — the shared-checkout shortcuts have now caused two separate incidents this session.
